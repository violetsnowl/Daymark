### PR-001 · 更新安装页仍被 MT管理器接住（未验证修复）

- **发现**：2026-10-08，内测用户（小米 14 Ultra / HyperOS），v0.1.10 → v0.1.11 更新时复现。
- **现象**：点「立即更新」后，安装环节没有进入系统安装页，而是直接打开 **MT管理器**
  （bin.mt.plus），并在 MT管理器内完成了安装。用户从未用 MT管理器装过应用。
  此前 v0.1.4 时代还出现过「选择打开方式」被 WPS 接住、来源记成第三方的情况（同族问题）。
- **影响**：功能可用（安装成功），但安装入口指向第三方应用属**非预期行为**：
  来源归属错误、依赖第三方 app 的实现、不同手机上行为不可控。
- **分析**：
  1. 安卓里多个应用可以声明自己能“打开 APK 文件”，MT管理器注册了 VIEW 处理器；
  2. 第一版挑选逻辑按包名含 `packageinstaller` + `MATCH_DEFAULT_ONLY` 查找，
     **MIUI 系统安装器未进该名单**，于是退到“列表里第一个能开 APK 的处理器” = MT管理器；
  3. **关键时序**：安装动作由“正在执行更新的那个版本”的代码发起——
     v0.1.11 里已把规则收紧为「只认 FLAG_SYSTEM 系统应用，找不到则不钉包交回系统默认」
     （提交 `32d0c09`），但本次 0.1.10→0.1.11 的安装仍由 0.1.10 的旧逻辑执行，
     **修复尚未被真正跑过**。
- **状态**：⏸ **搁置，待后续集中处理**（0.1.13/0.1.14 用户实测：安装选择器仍被第三方接住，与 0.1.11 修复预期不符；MT管理器等 VIEW 处理器仍胜出。已确认 FLAG_SYSTEM 枚举不够，需再查 MIUI 系统安装器 Intent-filter / 白名单。**保留在本册，勿关单。**）

### PR-002 · 服务器带宽瓶颈（根因未除）

- **发现**：2026-10-08 用户实测更新下载仅几百 KB/s；我方实测同线路 **39 KB/s（≈0.3 Mbps）**。
- **现状**：安卓下载源已切 GitHub CDN（v0.1.10 起）绕开；但**桌面端更新仍从服务器下载**、
  未来官网静态资源也在此服务器——根因（椰子云入门套餐带宽）未动。
- **处理方向**：升级 VPS 带宽套餐，或官网/静态整体迁 CDN（花钱项，待用户决策）。
- **状态**：⏸ 待决策（安卓侧已缓解，桌面 2.5MB 更新在最差情况下约 1 分钟，可忍）。

### PR-003 · 首启权限引导：小米机已验收通过；其他厂商系统未验（如实留痕）

- **验收**：2026-10-08 用户在小米（MIUI/HyperOS）真机**实测通过** ✅——通知授权随卡弹出、
  四行设置入口落点正确，引导闭环成立。
- **未验范围（如实记录）**：**仅小米一台机型**。华为 / OPPO / vivo / 三星等厂商的
  设置页层级与开关命名不同，按钮落点未在任何非小米设备上验证过；文案亦按 MIUI 撰写。
- **状态**：⏳ 本机型通过；他厂待首台真机出现时验证（发现落点错误即转「现存待修」常规修单）。

### PR-004 · 课程导入在供应商晚高峰可能连续超时（外部约束）

- **事实**：解析超时预算 300s、重试 2 次；实测出现过 240s×3 全失败（耗时约 12 分钟），
  根因为**供应商（DeepSeek）晚高峰服务端挂起**（DB 实证 preview 全空，与我方提取无关）。
- **影响**：晚高峰导入可能整轮失败，用户需改时段重试。
- **状态**：⏸ 已知外部约束（不修我方代码；可选缓解：失败文案提示"避开晚高峰重试"）。
